> 결과는 평소대로 `docs/handover/v<버전>.md`로 넘긴다. 이 파일은 bidwatch 쪽 기록이다(bid-collectors 저장소를 고치지 않는다).

## 1. 왜
- 나라장터 밖에서 자체 전자입찰을 하는 기관의 공고는 지금 **알리오로만** 받는다. 알리오는 제목·기관·날짜·첨부·원문 링크뿐이라
  (v1.3.0 `fetch_detail` 포함) 나라장터 공고처럼 예산·입찰 방식·참가 조건을 보여줄 수 없다(사용자 확인 2026-09-25: 한수원 ALIO-3579175).
- 알리오에도 없는 공고가 있다 — 국방(d2b) 하루 120~140건, 한전KPS·한전 계열 수의계약(`bidwatch/docs/procurement_sources_research.md` 3-2).
- 알리오는 **유지**한다(64개 기관을 수집기 하나로 받는다). 기관 수집기는 알리오의 보완이다(bidwatch plan.md 2026-09-25 판단).

## 3. 요청 — 두 단계
**① 조사 먼저(구현 전)**: 1~8번 각각
- 실제 호출 1~2회로 응답 필드·건수·페이지 구조·조회 기준일(공고일? 등록일?)·인증(활용신청 필요 여부, 별도 키)·호출 한도
- 공고 고유번호 필드와 **알리오 공고와 잇는 방법** — 알리오 제목에 기관 공고번호가 들어 있는 경우가 있다
  (실측 예: 한전 `[G052600469]…`, 수자원 `[B5202603347]…`, 한수원 `[K260668010]…`). 알리오 상세 `refrUrl`에도 기관 전자입찰 링크가 있다.
  → bidwatch가 중복 묶음(F-014)을 할 때 쓸 수 있는 키가 있는지.
- 결과를 표로(기관 | API 사용 가능 | 인증 | 하루 필요 호출 수 | 알리오와 잇는 키 | 추천) 보내 주면, **어느 기관부터 구현할지 사용자가 정한다.**

**② 구현(사용자가 고른 기관만)**: 기존 수집기와 같은 계약
- `Notice` 계약 그대로, `extra` = 응답 원문 전부(v1.2.5 원칙 ①), 실패·절단은 `errors`/`is_partial`(v1.1).
- **data.go.kr 하루 1,000회는 나라장터·K-Startup 등과 공유**한다 — 기관당 1회 수집 호출 수를 handover에 적어 달라.
- 사전규격·발주계획처럼 입찰공고가 아닌 것은 별도 메서드로(나라장터 확장 메서드와 같은 방식이면 좋다) — 입찰공고가 우선.
