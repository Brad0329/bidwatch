## 결정과 이유

- **정규화 방식 — 짧은 이름 통일 ("서울특별시" → "서울"):** 수집기마다 region 형식이 다름 (나라장터: "서울", 기업마당: "경기도"). DB 저장 시점에 normalize_region() 적용하여 짧은 이름으로 통일. ILIKE `%서울%`로 검색하면 정규화 안 된 데이터도 매칭되므로 하위호환 유지.
- **지역 목록 API — DB DISTINCT 대신 상수 반환:** DB에 수집된 데이터가 없는 지역도 드롭다운에 표시해야 함. 17개 시/도를 상수로 관리하여 일관성 보장.
- **멀티셀렉트 드롭다운 — 콤마 구분 문자열 전달:** API 파라미터: `region=서울,부산` (콤마 구분) → 백엔드에서 split → OR 조건 ILIKE. 단일 쿼리 파라미터로 처리하여 API 단순성 유지.
- **관심 지역 기본 필터 자동 적용:** useEffect + regionInitialized 플래그로 최초 1회만 적용. 사용자가 이후 수동으로 변경/해제 가능. 관심 지역 미설정 시 전체 지역 표시 (필터 없음).
- **tenant_profiles.region — 콤마 구분 문자열 저장:** ARRAY(String)으로 변경하면 마이그레이션 필요 → 콤마 구분 문자열로 저장하여 마이그레이션 회피. "서울,부산,경기" 형태.
- **프로필 API 신규 생성 (profile.py):** 기존에 프로필 라우터가 없었음. GET/PUT /api/profile/regions만 우선 구현 — Phase 3 AI 매칭에서 프로필 API 확장 예정.
- **검토요청 페이지에도 지역 필터 추가:** notices, pre-notices, review 3개 페이지 모두에 일관되게 적용.

## 실패한 접근 — 정확 일치 정규화 (2026-08-05 수정)

**증상:** region 값이 있는 공고 10,401건 중 5,906건(56%)이 17개 지역 필터 어디에도 안 걸림.

**원인 2가지:**

1. `normalize_region()`이 dict 정확 일치만 처리했는데, 실제 수집 데이터는 시군구가 붙은
   복합 문자열이었음. `"전라남도"` → `"전남"`은 되지만 `"전라남도 여수시"`는 원본 유지 →
   `%전남%` 필터에 안 걸림. 누락 상위값이 전부 이 패턴 (전라남도 여수시 59건, 순천시 44건 등).
   **신규 수집분도 계속 누락되는 구조였음.**
2. `normalize_region()`은 수집 시점에만 적용되는데 소급 반영이 없어서, 기존 17,627건은
   `"경상북도"`처럼 매핑 테이블에 있는 값조차 원본 그대로 남아 있었음.

**해결:** 정확 일치 → 접두어 일치 → 부분 일치 3단계로 변경 + 백필 스크립트 1회 실행.
결과: 필터 누락 56% → 32%. 남은 32%는 `"각 수요기관"`, `"한국환경공단"`, `"산업통상부"` 등
실제로 지역 정보가 없는 값이라 정상.

**접두어 매칭에서 주의할 점 — `"경기도 광주시"` 중의성:**
단순 substring 매칭을 쓰면 `"경기도 광주시"`(8건)가 광주광역시로 잘못 분류됨. 그래서
별칭을 **길이 내림차순으로 정렬해 접두어 매칭**한다 — `"경기도"`(3자)가 `"광주"`(2자)보다
먼저 검사되므로 경기로 올바르게 잡힘. `test_region.py::test_gwangju_is_not_confused_with_gyeonggi`가
이 회귀를 막는다.

**부분 일치를 4자 이상 별칭으로 제한한 이유:** `"재단법인 광주광역시 사회서비스원"`처럼 기관명
뒤에 지역이 오는 경우를 잡으려면 부분 일치가 필요하지만, 2자 별칭까지 허용하면 `"OO경기장"`이
경기로 잡히는 오탐이 생김. `"광주광역시"`, `"경상남도"` 같은 4자 이상 전체 명칭은 중의성이 없다.

**백필 스크립트:** `backend/scripts/backfill_regions.py` (`--dry-run` 지원).
distinct 값 단위로 UPDATE하므로 행 수(1.7만)가 아니라 고유 표기 수(2,906)만큼만 쿼리한다.
정규화 로직을 바꾸면 다시 실행해야 기존 데이터에 반영된다.
